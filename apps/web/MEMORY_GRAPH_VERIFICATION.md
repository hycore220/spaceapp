# Memory graph verification

The 3D Memory Atlas supports streamed layout and WebGL2 drawing for large graphs.
This guide explains how to reproduce its checks and interpret the measurements
for [issue #62](https://github.com/oll4com/spaceapp/issues/62). The response limit,
layout, renderer and measurement method have separate contracts.

## Data and layout

The admin overview keeps its default 2,000-node budget and accepts an explicit
`limit` up to 50,000, with at most three selected edges per requested node. Its
admin guard and label redaction remain in place. Cache validators distinguish
query variants, including filtered requests at the default limit. Only the
unfiltered legacy response retains the plain snapshot revision as its ETag.

The existing layout worker publishes a usable seed before completing layout.
Up to 2,000 nodes, its final coordinates use the original `layoutMemoryNetwork3D`.
Above that size, `createProgressiveMemoryLayout` uses ID-sorted nodes/edges,
deterministic XYZ seeds and bounded repulsion representatives. It publishes
every fourth iteration through iteration 60. The same input has repeatable
output, including reordered node/edge arrays; final positions can differ from
the original 180-step algorithm. The maintainer explicitly permits that change
under determinism and existing-test requirements in
[the layout clarification](https://github.com/oll4com/spaceapp/issues/62#issuecomment-6222726217).

Workers own graph preparation and BVH refits. Topology/style buffers transfer to
the UI once, while subsequent messages transfer coordinates and BVH bounds.
Cancelled generations stop publishing. Camera movement reuses uploaded buffers.
Canvas fallback keeps at most 2,000 nodes and 6,000 edges when WebGL2 is unavailable
or lost; restoration is handled when the browser delivers its restored event.

## Reproduce the feature and tests

Use the repository's Node version and isolated development checkout as described
in [CONTRIBUTING](../../CONTRIBUTING.md). Linux is the reference environment;
WSL is suitable for the development suite. Do not reuse an operator's credentials,
database, sockets or browser profile.

```sh
ELECTRON_SKIP_BINARY_DOWNLOAD=1 npm ci
npm run check
npm test
npm run build
npm run hygiene:preflight
npm run dev:web
```

Open `/demo-workspace`, then Workspace → Memory → Atlas → 3D. The demo-only
Synthetic nodes selector offers 100, 2,000, 10,000 and 50,000 nodes without a backend
or embeddings provider. Test drag, wheel/pinch, keyboard rotation/zoom, hover,
click and Titles both during convergence and after completion. Choose Archive
again to verify canonical search and detail navigation. Synthetic fixture names
and colors differ from a real archive's topic/month groups.

`memory-graph-review.html` mounts the actual component with explicit diagnostics.
Its API-shaped load button uses generated bytes and the production decoder,
validation worker, UI delivery and layout. This source page does not benchmark a
production HTTP server or authentication/database path. A separate controlled
HTTP fixture harness must be labelled with its transport and byte count.
`memory-graph-benchmark.html` is a standalone diagnostic and must not be presented
as a full workspace test.

## Distinguish the timing populations

| Measurement | What it covers | What it does not establish |
| --- | --- | --- |
| Raw rAF intervals | Consecutive animation callback timestamps while the real component rotates and zooms | Pure GPU work, physical scanout or input latency |
| CPU submission including labels | JavaScript draw/label callback duration | Asynchronous GPU completion or presented-frame cadence |
| Chrome presentation cadence | Intervals between the trace's matched presentation endpoints | Callback-to-present latency, physical scanout or guaranteed GPU headroom |
| Synchronous BVH picking | One query against uploaded data and the cached rendered camera | Whole pointer-event or input-to-present latency |
| Main-thread load tasks | Whole tasks overlapping the defined load/layout/render observation window | Worker execution time or production auth/database latency |
| Server response timing | The stated route/provider/serialization harness | Costs outside that harness or actual transfer compression |

The component harness runs 30 warmup callbacks followed by 240 measured intervals.
Reports retain raw intervals and CPU samples. Summary quantiles sort a copy and
select index `floor(sampleCount * quantile)`; aborted/empty runs retain their
status and null empty metrics. CPU sample i runs at interval i's ending callback,
so its work can affect the following interval. Do not substitute CPU time for
rAF intervals or discard scheduling delays to obtain a passing threshold.

A Chrome trace can independently match predecessor-anchored request/presentation
endpoints to the recorded window. Keep the mapping script, trace, source identity,
hardware, viewport/DPR, Titles state and scene with the report. Full-scene evidence
includes labels and all graph edges/nodes. Empty/node-only/edge-only/native-line
variants and GPU timer queries are diagnostics with different eligibility or
overhead; their results do not silently replace the full-scene measurement.

## Loading and picking evidence

The load diagnostic emits `spaceapp-memory-api-load-window` with exact start/end
timestamps. Its end is bounded by matching-payload layout completion, an actual
render-return attribute update, two animation callbacks and a future task. This
bounds CPU render submission, not initial GPU upload completion or presentation.

Retain the full duration of every overlapping main-thread task, including tasks
crossing either boundary. The Long Tasks observer drains before and after two
future tasks. Unsupported observation, errors, incomplete load, reported drops
or missing optional browser drop metadata make completeness unknown. A missing
count is not zero, and an empty entry array is not 0 ms of CPU work. A native Chrome
trace can provide separate task observations while retaining its own completeness
limits. Keep worker tasks separate from the main-thread responsiveness criterion.

Picking evidence should include cold calls, multiple camera poses, hits, misses,
in-viewport misses, near-node queries and boundaries. Retain every raw duration
and the corresponding uploaded graph/camera. A finite observed maximum supports
that sample population; it does not prove a universal worst-case bound.

## Recorded evidence and its limits

The accompanying evidence package labels each source generation and its actual
commands. The recorded laptop is MacBookPro17,1, Apple M1 integrated 8-core GPU,
16 GiB, macOS 26.1, Chrome 155 Guest/ANGLE Metal. Frame captures use Titles on,
full scene, GPU queries off, DPR 2 and a 857.1875×475.40625 CSS canvas with a
1714×951 drawing buffer. Renderer/layout/picking behavior must be tied to the
source hashes or documented executable-equivalence check, not a later label.

The frame captures below were collected on R24; picking supplements were
collected on R25 and the fresh loading/recovery capture on R26. They are
historical measurements, not new R27 captures. The R27 source audit verifies
comment-stripped renderer/layout/picking equivalence; API cache variants and
parser error handling changed separately. See the packet source/evidence map.

The preserved Chrome presentation-cadence p95 values are 16.667 ms at both 2k/6k
and 50k/150k. Raw rAF p95 is about 17.6 ms, which fails the strict 2k 16.7 ms rAF
comparison. The reports keep that discrepancy and whole-trace dropped-frame
events; the presentation interpretation remains subject to maintainer review.

One controlled 31,856,629-byte HTTP load on a fresh diagnostic page had an exact
6,574.5 ms window with 3,733 overlapping main-thread tasks, maximum 11.525 ms and
no observed task over 100 ms. A previous load with about 1.2 MB of raw picking text
already in the live diagnostic report had four tasks over 100 ms, maximum
14,407.463 ms. Both traces remain attached. Large report DOM, accessibility queries
and DevTools effects are candidate causes; their sole contribution is unproven.
Fresh-page conditions are disclosed rather than subtracting alleged overhead.
Observer/trace loss completeness remains unknown where affirmative metadata is
absent. These are controlled-window observations, not universal production claims.

The separate route benchmark uses a preprocessed in-memory snapshot provider over
loopback Fastify HTTP. It reports 17,706,054 response bytes and 222.420–232.786 ms
server timing at 50k/150k. Offline gzip 1,145,839 B is not measured transferred
compression. Production sessions, database/provider work and migrations are
outside that timing scope; authentication/redaction have separate API tests.

Functional recovery evidence distinguishes real `WEBGL_lose_context` events from
an explicit `getContext('webgl2') === null` simulation. A manual hold interval
includes deliberate waiting and cannot be reported as automatic recovery latency.
Prior failed/incomplete captures remain preserved. Simulated API absence is not
a physical-GPU-absence or Chrome `--disable-webgl` result.

## Submission and review

Keep raw reports and traces outside the source tree so hygiene checks can reject
generated/runtime files. Retain failed attempts and optional test skips, and
distinguish local checks from the eventual PR's CI. CodeRabbit feedback and its
pre-merge checks do not replace the maintainer's acceptance criteria or the
actual contributor's required review/test and DCO consent.
